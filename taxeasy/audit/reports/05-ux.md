## 2. Navigation — Bouton Retour

### Bug E1 : Reconstruction de l'historique après refresh

**Statut : CORRIGÉ**

`wizard.store.ts` ligne 31–34 :
```typescript
setDeclaration(declarationId, answers, currentNodeId) {
  const path = engine.buildPath(answers);
  const currentIdx = path.indexOf(currentNodeId);
  const history = currentIdx > 0 ? path.slice(0, currentIdx) : [];
  set({ declarationId, answers, currentNodeId, history });
},
```

L'historique est correctement reconstruit via `engine.buildPath(answers)` à chaque initialisation. Après un refresh, le bouton Retour fonctionne normalement.

### Vérification `canGoBack`

`useWizard.ts` : `canGoBack = store.history.length > 0` → correct.

`WizardNavigation.tsx` : le bouton Retour est `disabled={!canGoBack}` → correct.

**Note UX MEDIUM** : Si `canGoBack` est `false`, le bouton est désactivé mais reste visible. L'utilisateur ne sait pas pourquoi il ne peut pas revenir en arrière (pas de tooltip ni de message explicatif). Idéalement, masquer le bouton ou afficher un tooltip "Première étape".

## 3. Affichage des erreurs et état de chargement

### Messages d'erreur

- **WizardShell.tsx** : affiche un `<Alert variant="destructive">` quand `error !== null` — ✅ visible
- **useWizard.ts** : `engine.validateAnswer()` retourne une erreur string, stockée via `store.setError()` — ✅
- **DocumentUpload.tsx** : en cas d'échec d'upload, le badge "Erreur" est affiché dans la liste des fichiers — ✅ visible
- **LoginPage.tsx** : `<Alert variant="destructive">` pour les erreurs auth — ✅

**Problème MEDIUM** : Dans `DocumentUpload.tsx` (ligne 61), l'erreur d'upload est affichée via un `Badge variant="destructive"` dans la liste de fichiers, mais **sans message d'erreur détaillé** pour l'utilisateur. L'erreur serveur (`err.error`) est récupérée via `throw new Error(err.error)` mais n'est pas exposée dans l'UI — l'utilisateur voit uniquement "Erreur" sans savoir si c'est un problème de taille, de format, ou réseau.

**Problème MEDIUM** : La sauvegarde auto silencieuse (`console.warn` uniquement en cas d'échec) ne notifie pas l'utilisateur. Si le réseau tombe entre deux étapes, les réponses semblent sauvegardées mais ne le sont pas.

### État de chargement (isSaving)

- `WizardShell.tsx` : indicateur `● Sauvegarde automatique` visible avec `animate-pulse` — ✅
- `WizardNavigation.tsx` : bouton "Suivant" disabled pendant `isSaving`, plus label "Sauvegarde…" — ✅
- `SummaryStep.tsx` : skeleton animé pendant le fetch du calcul fiscal — ✅

## 5. Validation des champs

`engine.validateAnswer()` gère :
- Champs obligatoires (valeur vide) → "Ce champ est obligatoire."
- `number`/`number_chf` : valeur NaN ou < 0, min/max
- `multi_choice` : au moins une option sélectionnée

**Problème LOW** : Pour le type `number` inline (dans `StepRenderer.tsx`), la conversion `parseInt(e.target.value, 10) || 0` force silencieusement la valeur à 0 si l'input est vide ou invalide, sans afficher d'erreur immédiate. L'erreur apparaît seulement au clic "Suivant". Sur mobile, saisir une valeur négative ou alphabétique avant de cliquer Suivant est déroutant.

**Problème LOW** : `NumberCHF.tsx` accepte le montant 0 sans warning pour les nœuds non-optionnels. `engine.validateAnswer` considère `0` comme valide (`value !== ""` et `num >= 0`), mais 0 CHF pour un salaire brut est rarement intentionnel — aucune confirmation demandée.

## 7. Accessibilité

### Labels et inputs associés

| Composant | Observation | Statut |
|-----------|-------------|--------|
| `SingleChoice.tsx` | `<Label htmlFor={option.value}>` + `<RadioGroupItem id={option.value}>` | ✅ |
| `MultiChoice.tsx` | `<Label htmlFor={option.value}>` + `<Checkbox id={option.value}>` | ✅ |
| `NumberCHF.tsx` | `<Label htmlFor={node.id} className="sr-only">` + `<Input id={node.id}>` | ✅ (masqué visuellement mais présent pour screen readers) |
| `number` inline (StepRenderer) | `<Input type="number">` sans `id` ni `<Label>` associé | ❌ |
| `LoginPage.tsx` | `<Label htmlFor="email">` + `<Input id="email">` | ✅ |

**Bug MEDIUM** : Le renderer `number` inline dans `StepRenderer.tsx` n'a pas de `<label>` associé, ni d'`id` sur l'`<Input>`. Les screen readers ne peuvent pas identifier le champ. Correctif : ajouter `id={node.id}` à l'Input et un `<label htmlFor={node.id}>` comme dans `NumberCHF`.

### Messages d'erreur — role alert

| Composant | Composant utilisé | `role="alert"` |
|-----------|-------------------|----------------|
| `WizardShell.tsx` | `<Alert variant="destructive">` | Dépend de l'implémentation shadcn/ui |
| `LoginPage.tsx` | `<Alert variant="destructive">` | Dépend de l'implémentation shadcn/ui |

**Vérification** : `src/components/ui/alert.tsx` doit exposer `role="alert"` pour que les messages d'erreur soient annoncés par les lecteurs d'écran.

### Images et icônes

- `DocumentUpload.tsx` : SVG upload sans `aria-label` ni `aria-hidden="true"` sur l'icône décorative — **MEDIUM** pour screen readers (l'icône sera lue sans contexte)
- Marketing page : pas d'`<img>` réelles (mockup UI en HTML/CSS pur) — ✅
- Emojis dans le dashboard et la landing page (🧾, ⚠️, ✨…) : sans `aria-hidden` — lisibles mais verbeux pour les screen readers

### Boutons descriptifs

- `WizardNavigation.tsx` : bouton "← Retour" avec texte visible — ✅
- `WizardNavigation.tsx` : bouton "Suivant →" / "Terminer" / "Continuer →" selon contexte — ✅
- `DashboardPage.tsx` : bouton "+ Nouvelle déclaration" — ✅
- `DocumentUpload.tsx` : zone de drop clickable (`<div onClick>`) sans `role="button"` ni `tabIndex={0}` — ❌ non accessible au clavier
